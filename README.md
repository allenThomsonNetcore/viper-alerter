# Viper catalog indexing alert service

Viper checks scheduled catalog-indexing runs, sends state-change and recovery alerts through EmailJS, and stores run/alert history in Supabase. A small Flask dashboard shows the newest recorded status for each site and links to the platform's actual status API.

The CSV header is `site_key,region,cron,max_duration_minutes,version,app`. `version` must be `v1` or `v2`; `app` must be `shopify` or `bigcommerce`. The dashboard and alert email include both values.

The home page also shows each configured site's cron expression with a plain-language description. Cron schedules are evaluated in UTC; run and check timestamps in the dashboard are displayed in IST.

## How the service runs

- Render runs the web application and dashboard.
- `/live-status` reads the configured site CSV and fetches the latest entry from each site's status API when opened; timestamps are shown in the viewer's local time zone.
- cron-job.org calls the authenticated `POST /internal/run-checks` endpoint every 30 minutes. The check is synchronous, so the request returns after that run has completed.
- Supabase stores scheduled run snapshots and successful notification deliveries. The browser never receives the Supabase service-role key.
- The optional `GET /healthz` endpoint can be pinged by an uptime monitor. It is not the scheduler and does not run checks.

## Supabase setup

Create a Supabase project, open its SQL Editor, and run [`supabase/schema.sql`](supabase/schema.sql). Copy the Project URL and server-side `service_role` key into Render environment variables. Keep the service-role key private; the dashboard accesses the database only through the Flask backend. The schema enables RLS without granting browser roles direct access.

The dashboard's **Add site** form stores new site configurations in the `site_configs` table. Dashboard deletions create a disabled site override, so a deleted site stays excluded even if it is still present in the CSV; existing run history is retained. Re-run the latest schema in the Supabase SQL Editor before deploying these features. Dashboard site entries are merged with the CSV site list and checked by the same scheduler.

If a logged-in dashboard gets a Supabase 403, verify `SUPABASE_URL` and the key are from the same project, then rerun the schema so its `service_role` grants are applied. New `sb_secret_...` keys are sent only in the `apikey` header; legacy service-role JWTs are also sent as a Bearer token.

Supabase Free is useful for a prototype, but projects can be paused after a week of low activity, storage is limited, and automatic backups are not included. This service writes data during every checker run, but export important data periodically. See [Supabase Free plan limits](https://supabase.com/pricing), [project pausing](https://supabase.com/docs/guides/platform/free-project-pausing), and [database backups](https://supabase.com/docs/guides/platform/backups).

## EmailJS setup

Create an EmailJS service and email template. Paste [`emailjs/template.html`](emailjs/template.html) into the template's **Code** editor. Set **To email** to `{{to_email}}`, **Subject** to `{{subject}}`, **CC** to `{{cc_emails}}`, and **BCC** to `{{bcc_emails}}` (leave CC or BCC blank if unused). The HTML uses these template variables:

| Template variable | Value |
|---|---|
| `to_email` | Recipient configured as `EMAILJS_TO_EMAIL` |
| `cc_emails` | Comma-separated CC recipients from `EMAILJS_CC_EMAILS` |
| `bcc_emails` | Comma-separated BCC recipients from `EMAILJS_BCC_EMAILS` |
| `subject` | Alert subject generated by Viper |
| `message` | Plain-text alert body |
| `site_key` | Site key, when present |
| `region` | Region ID, when present |
| `version` | Integration version (`v1` or `v2`) |
| `app` | Commerce app (`shopify` or `bigcommerce`) |
| `state` | Alert state, when present |
| `expected_cause` | Likely feed pull pipeline failure for a `missing` status; verify using pipeline logs |
| `scheduled_time` | Scheduled time in IST, when present |
| `checked_at` | Time Viper checked the API, in IST |
| `api_timestamp` | Latest API entry timestamp converted from its epoch value to IST, when present |
| `status_url` | Platform status API URL, when present |

Alert email timestamps use IST. The API's raw `date` text is omitted because its timezone is not specified by the endpoint; use `api_timestamp` for an unambiguous timestamp.

Set `EMAILJS_SERVICE_ID`, `EMAILJS_TEMPLATE_ID`, `EMAILJS_PUBLIC_KEY`, `EMAILJS_TO_EMAIL`, and (if enabled for the account) `EMAILJS_PRIVATE_KEY` in Render. Add optional comma-separated `EMAILJS_CC_EMAILS` and `EMAILJS_BCC_EMAILS` lists for additional recipients. In the EmailJS template settings, set **CC** to `{{cc_emails}}` and **BCC** to `{{bcc_emails}}` (leave either field blank if unused). The app calls EmailJS over HTTPS. A delivery row is written to Supabase only after EmailJS returns success.

## Slack alerts and channel selection

For direct messages, add the bot scopes `chat:write` and `im:write` to your Slack app, then reinstall the app to the workspace. Set its Bot User OAuth Token as `SLACK_BOT_TOKEN` in Render and comma-separated Slack user IDs as `SLACK_RECIPIENT_IDS` (currently `U0AE968E7H6`). Keep the bot token private. Viper opens a DM with each user and posts the alert through Slack's `chat.postMessage` API. All recipients must belong to the workspace where the app is installed. The legacy `SLACK_WEBHOOK_URL` remains supported if no bot token and recipient list are configured.

Set `ALERT_CHANNEL` in Render to `email`, `slack`, or `both`. It defaults to `email` to preserve the existing behavior. `slack` and `both` require either `SLACK_BOT_TOKEN` plus `SLACK_RECIPIENT_IDS`, or the legacy `SLACK_WEBHOOK_URL`; `email` requires the EmailJS settings above. When using `both`, successful channel deliveries are tracked separately so a retry after one channel fails does not resend to a channel that already succeeded. Add more Slack recipients by separating their user IDs with commas.

## Render setup

1. Push this branch (`feat_service_method`) to the Git remote connected to Render.
2. Create a Web Service for the repository, using the included [`render.yaml`](render.yaml) Blueprint settings or these commands:

   ```sh
   pip install -r requirements.txt
   gunicorn --bind 0.0.0.0:$PORT --workers 1 checker.web:app
   ```

3. Add the Supabase, EmailJS, dashboard, and trigger secrets from [`.env.example`](.env.example) in Render's environment settings. Configure `FLASK_SECRET_KEY` as a long random secret. `render.yaml` generates it automatically for Blueprint deploys and enables secure session cookies.
4. Configure cron-job.org with a job scheduled as `*/30 * * * *` (UTC):
   - Method: `POST`
   - URL: `https://<render-service>.onrender.com/internal/run-checks`
   - Header: `Authorization: Bearer <RUN_TRIGGER_TOKEN>`
   - Do not include the response body in third-party execution history if it contains any operational details.
5. Optionally configure a separate five-minute `GET https://<render-service>.onrender.com/healthz` monitor to wake a sleeping free web service. It is not required for correctness: the scheduled POST itself wakes the service. If the app has slept, the first request can take about a minute to start.
6. Open the Render URL and sign in using the configured dashboard username and password. The home page refreshes every 60 seconds. Select a site key for its recent run history, or use “Open API” to open its real platform status endpoint.

Render Free web services spin down after 15 minutes without inbound traffic, can restart at any time, and share 750 free instance hours per workspace per month. A five-minute ping will keep the service active for most of the month. The external 30-minute POST is the important schedule trigger; the ping is optional. cron-job.org supports custom HTTP methods and headers but does not guarantee exact invocation times. For dependable production alerts, use paid always-on compute and a scheduler with an operational guarantee. See [Render Free limits](https://render.com/docs/free) and [cron-job.org FAQ](https://cron-job.org/en/faq/).

## Local development

```sh
python3.12 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Set local Supabase, EmailJS, and dashboard values before running.
set -a && . ./.env && set +a
gunicorn --bind 127.0.0.1:10000 --workers 1 checker.web:app
```

Visit `http://127.0.0.1:10000`. For a local check, send an authenticated request:

```sh
curl -X POST http://127.0.0.1:10000/internal/run-checks \
  -H "Authorization: Bearer $RUN_TRIGGER_TOKEN"
```

## Data and API

- `GET /login` — dedicated dashboard sign-in page
- `GET /` — dashboard (authenticated session)
- `GET /site/<site_key>?region=<region>` — run history (authenticated session)
- `GET /api/sites` and `GET /api/sites/<site_key>` — JSON status API (authenticated session)
- `POST /internal/run-checks` — protected external scheduler trigger
- `GET /healthz` — health ping; no checker work is run

The `site_runs` table is unique on `(region, site_key, scheduled_time)`, so each scheduled run updates its status. The newest history entry in that run window determines its current state. `alert_deliveries` records alert episodes: repeated checks of the same failure are deduplicated, recovery sends one message, and a later failure after recovery starts a new episode. If one checker cycle finds an older failed/missing run and a newer successful run, it sends a recovery notice describing both and suppresses the stale failure alert. Run the latest `supabase/schema.sql` before deploying to add the recovery metadata column. Records older than seven days are pruned on checker runs.

## Assumptions and limits

- `TIMESTAMP_SEMANTICS` defaults to `finish`; confirm the platform's actual `timeStamp` meaning. Status classifications are defined in [`checker/evaluator.py`](checker/evaluator.py).
- The dashboard shows latest observations and the latest history stored by the checker; it does not query the status endpoint on every page load.
- `ACCEPTED` and `QUEUED` API statuses are treated as in-progress. They do not trigger failure alerts while within the configured duration and buffer; if they remain active beyond that deadline, they are classified as `stuck`.
- `ABORTED` is treated as a failed run and triggers the standard failure alert, including the API status message when available.
- `POST /internal/run-checks` returns `202` as soon as a cycle starts. The check keeps running in the web process after the response, so a larger site list does not hit Render's request timeout. A second trigger while that cycle is still running returns `409`. On the free plan the process can still stop after 15 minutes without inbound HTTP traffic, or if Render restarts the service.
- The free Render service may cold-start or restart, and cron-job.org can be delayed. This is suitable for a prototype, not an alerting SLA.
